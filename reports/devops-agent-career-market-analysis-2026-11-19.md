## 一、结论先行

### 1. 一句话判断

这个仓库能支撑你进入 **DevOps / CI-CD / 初级云原生平台工程** 的面试准备；如果目标是 **AI Agent / LLM 应用开发**，目前还缺少最关键的一层就业证据：一个可运行、可测试、可评测、可部署，并能说明成本和可靠性的 Agent 项目。

你的合理定位不是“算法工程师”，而是：

> **DevOps / 平台工程背景 + AI Agent 应用工程能力**

首选岗位是 **AI Agent / LLM 应用开发工程师**；最贴合当前履历的过渡岗位是 **AIOps / AI DevOps / Agent 平台工程师**；第二落点是 **RAG / 企业知识库应用工程师**。

### 2. 当前能支撑什么

| 能力方向 | 当前证据 | 可支撑程度 | 招聘市场解释 |
| --- | --- | --- | --- |
| Git / GitHub 协作 | 大量分支、PR、模板、提交记录 | 可写进简历，达到初级岗位要求 | 基础门槛，不构成差异化 |
| GitHub Actions CI | lint/test/build、matrix、cache、artifact、outputs、真实排障 | 可支撑 CI/CD 初级岗位 | 是当前最有可信度的工程资产 |
| Docker / GHCR | 多阶段构建、Compose、GHCR、Trivy、SBOM | 可支撑容器交付基础岗位 | 仍需修复扫描对象、推送对象不一致的问题 |
| CD / Environments | 三环境设计、审批说明、模拟部署脚本 | 可讲设计，不足以证明真实发布能力 | 缺真实部署、回滚、审批和故障演练 |
| Kubernetes | 8 个基础清单、killercoda 练习、Probe/PVC 日志 | 达到入门认知和实验级 | 尚未把自身应用完整部署进本地集群并排障 |
| AI / Agent | 约 170 KB 文档、少量代码片段 | 主要是 L1-L2 阅读与解释 | 没有 Python 项目、依赖、测试、评测集、服务 |
| RAG / Tool Calling / Evals | 文档中能解释概念 | 尚不能视为工程能力 | 面试会追问检索指标、失败案例、成本和回归测试 |

### 3. 当前不能支撑什么

不建议直接定位为大模型算法工程师、训练工程师、CUDA / 推理引擎工程师、高级 K8s 平台工程师或高级 SRE。仓库没有模型训练、分布式训练、推理优化、大规模集群治理、生产 SLO 或真实线上故障经验，岗位年限也不匹配。

## 二、仓库学习进度与真正卡点

### 1. 进度事实

- 75 天主线已记录到 Day 49，约完成 65.3%。
- 最后明确学习日志约在 2026-07-26；最后仓库提交是 2026-10-22。
- 原计划剩余 26 个学习日，按每天 3 小时约 78 小时。
- 当前主要不是知识输入不足，而是开放式 Agent 项目没有形成本地反馈闭环。

### 2. 卡点为什么出现在这里

前 49 天以命令、YAML 和 CI 结果为主，正确与否很容易验证。进入 ACK、GitOps 和 Agent 后，学习目标变成“设计一个系统”，同时开始依赖云账号、集群和模型 API。任务变大、反馈变慢，进度就容易中断。

因此，后续不应继续按“Day 50、Day 51”补日历，而应按以下顺序推进：

1. 先修复仓库中能被自动验证的工程问题。
2. 先做不用 LLM 也能运行、测试和排障的确定性 Agent。
3. 再接入模型、RAG、工具调用和评测。
4. 最后做 K8s、可观测性和作品化。

### 3. 必须优先修复的 P0 问题

- `/healthz`、`/readyz` 当前实际落到欢迎页并返回 200，不能证明应用健康。
- Docker workflow 不会因 `app/src/**` 改变而可靠触发。
- CD 没有明确等待 CI、构建和扫描成功。
- 扫描的镜像与随后重新构建并推送的镜像不是同一份制品。
- `scripts/deploy.sh` 使用 `-p 80:80`，而应用监听 3000。
- 部分 workflow 缺少显式最小权限。

这些问题会直接影响“你是否真的掌握 CI/CD”这一简历主张，应在开始 Agent 新功能前修掉。

- 54% 的程序员称过去一年公司发生岗位优化，25.7% 选择转向 AI 开发。

这些数据证明了 AI 能力的市场溢价和岗位扩散，但 60K 左右的全 AI 平均被 AI 科学家、算法研究员、AI Infra、大模型算法和高性能计算显著拉高。2026 年 1-4 月 AI 科学家 / 负责人平均月薪约 132,796 元，不代表 Agent 应用开发岗位的普遍水平。

## 五、三条最现实的目标岗位

### 1. 首选：AI Agent / LLM 应用开发工程师

**匹配你的原因：** AI 偏好最强，当前 DevOps 背景可以转化为工具调用、CI/CD 场景和部署能力。

**当前差距：** Python 工程、API 服务、结构化输出、RAG、工具调用、上下文管理、评测、可观测性、成本和失败恢复。

**最合适的差异化作品：**

> CI 失败日志 -> 脱敏 -> 规则解析 -> RAG 检索运维手册 -> 只读 GitHub 工具调用 -> 结构化诊断与修复建议 -> 自动评测和回归门禁。

它比通用聊天机器人更贴近企业痛点，也能同时证明 Agent、RAG、Tool Calling、Evals 和 DevOps。

### 2. 最贴合履历：AIOps / AI DevOps / Agent 平台工程师

**匹配你的原因：** CI/CD、容器、K8s、安全和故障复盘是已有积累；市场需要能把 AI 接入研发流程的人。

**当前差距：** 平台岗位通常要求 3-5 年经验，且要求 K8s、可观测性、SLO、权限治理和真实规模经验。当前仓库只达到入门实验级。

**可行进入路径：**

- 先从中小公司的 AIOps、DevOps 自动化、发布平台或内部工具岗切入。
- 或在现有工作中把 Agent 接入 CI 失败分析、PR 总结、发布检查，形成工作成果。
- 不在简历中把 49 天练习表述成“精通 Kubernetes / 高级 SRE”。

### 3. 第二落点：RAG / 企业知识库应用工程师

**匹配你的原因：** 企业落地需求明确，知识库、Runbook、文档和运维场景与你的资料积累相符。

**当前差距：** 不能只会“向量库 + Chat UI”，还要会数据清洗、切片、混合检索、Rerank、引用、权限、质量评测和更新机制。

**作品验收：** 提供 30-50 个问题作为 golden set，分别测召回、引用正确性、答案忠实度、无答案拒答、延迟和成本，并保留失败案例。

### 4. 保底方向

当前仓库经过 P0 修复和一次本地 K8s 部署后，可支撑 **CI/CD 工程师、发布工程师、初级云原生平台工程师** 的面试。这个方向不是失败，它可以作为现金流和工程经验的跳板；入职后继续把 AI Agent 嵌入研发流程，比脱产追逐“算法岗”更现实。

## 七、8 周高强度补齐方案

建议强度为每周 18-24 小时：工作日 5 天，每天 2 小时；周末 8-12 小时。这个强度高于原计划的每天 3 小时，但必须用可运行证据验收，不能再用文档页数衡量。

### W1：修复反馈回路，回到可验证工程

**产出：**

- 修复 `/healthz`、`/readyz` 并补测试。
- 修复 Docker workflow 应用代码触发。
- 让部署依赖测试、构建和扫描成功。
- 修复端口和最小权限。
- 用 kind / minikube 部署自身应用。

**验收：** 一条命令启动，探针语义正确，Pod Ready，CI 变绿，失败时能解释原因。

### W2：做确定性 CI Failure Analyzer

**产出：**

- 新建 `agent-platform` 独立仓库。
- Python 包、CLI、JSON Schema、日志读取、secret redaction。
- 识别失败 job、step、关键错误片段。
- 至少 10 个 failure fixture 和 pytest。

**验收：** 不接 LLM 也能稳定运行；同一输入输出可重复；敏感信息测试通过。

### W3：LLM 作为可替换组件

**产出：**

- provider adapter，支持 timeout、retry、限流和错误分类。
- 强制结构化输出并做 schema 校验。
- 记录 prompt、model、token、延迟、估算成本。
- 失败时可退回规则结果。

**验收：** 没有 API key 仍能跑测试；模型失败不会让服务崩溃；能解释一次调用的成本与延迟。

### W4：加入 RAG，而不是只做向量库演示

**产出：**

- 导入 CI/CD、K8s、Docker 和项目 Runbook。
- chunk、embedding、Top-K、引用、Rerank 和去重。
- 无答案时拒答；引用不到来源时明确标记。
- 建立检索问题集和基线指标。

**验收：** 能展示一次“检索错 -> 分析原因 -> 调整 -> 指标改善”的完整记录。

### W5：工具调用与只读 GitHub 集成

**产出：**

- 只读 GitHub API：读取 workflow run、失败日志、PR 文件。
- 工具 schema、权限白名单、超时、重试和审计日志。
- 可选本地 MCP Server。

**验收：** 工具参数非法、权限不足、超时和空结果都有可读错误；不会执行写操作。

### W6：Evals、Guardrails 与 CI 回归门禁

**产出：**

- 30-50 条 golden set，覆盖步骤识别、错误归因、引用、泄露、无答案和工具失败。
- 指标：准确率、schema 合法率、引用正确率、泄露数、P95 延迟、平均成本。
- 在 CI 中设置最低门槛并保存报告。

**验收：** 修改 prompt 或模型后能自动发现效果回退；失败样例进入回归集。

### W7：部署、可观测性与故障演练

**产出：**

- Docker 镜像、K8s Deployment / Service / ConfigMap / Secret 引用。
- readiness / liveness、资源限制、结构化日志、trace 或 request id。
- 注入模型超时、GitHub 429、坏日志、空检索和容器重启。

**验收：** 5 分钟内从零启动并演示；能定位一次人为故障；README 有架构图和限制。

### W8：作品化和岗位校准

**产出：**

- 2 分钟演示视频、架构图、自动截图、CI badge、评测报告。
- 一页简历项目描述：场景、方案、指标、失败处理、成本。
- 收集目标城市 20-30 条真实 JD，统计 must-have 与加分项。
- 按匹配度分 A/B/C 三档投递，每周复盘面试问题。

**验收：** 陌生工程师能在 10 分钟内运行项目；面试时能用数据解释为什么这样设计。

## 八、薪资与投递层级怎么对齐

由于没有提供当前城市、工作年限、学历和现有薪资，不能替你计算涨幅。下面给的是决策规则，而不是对个人 offer 的预测。

| 当前情况 | 8 周后优先投递 | 合理标价区间 | 不建议 |
| --- | --- | ---: | --- |
| 0-2 年，当前低于 15K | 初级 AI 应用、RAG 应用、DevOps 自动化 | 15-25K | 直接冲大厂算法或 40K+ Agent 专家岗 |
| 已有 DevOps / 运维经验，当前 15-25K | AIOps、Agent 平台、AI 应用开发 | 20-30K | 只改简历不补可运行项目 |
| 当前 25K 以上 | AIOps / Agent 平台 / 内部转岗 | 25-40K | 为“AI”标签接受明显降薪或纯外包试错 |
| 有大厂面试但无 AI 项目 | 先补 W2-W6 再投 | 依据原岗位级别 | 用 170 KB 文档证明工程能力 |

关键不是“学完 AI 就应该拿 60K”，而是让岗位、城市、年限和证据同时匹配。全 AI 平均薪资不是个人定价；具体招聘标价也不是 offer。

## 九、简历定位与表达边界

### 推荐定位

> DevOps / 云原生学习背景，具备 GitHub Actions、Docker、GHCR、Trivy 和 K8s 基础；正在构建面向 CI/CD 场景的 AI Agent，覆盖 RAG、Tool Calling、结构化输出、Evals、可观测性和本地 K8s 部署。

### 当前可写

- 搭建 GitHub Actions CI，使用 matrix、cache、artifact、workflow outputs 并完成失败排障。
- 构建 Docker 镜像并接入 GHCR、Trivy、SARIF 和 SBOM 检查。
- 设计 dev / staging / prod 环境与人工审批流程。
- 整理 K8s Probe、ConfigMap、PVC 等基础实验与故障复盘。

### 8 周后再写

- 开发 CI Failure Agent，完成日志脱敏、失败步骤识别、RAG 检索和只读 GitHub 工具调用。
- 建立 30-50 条 golden set，在 CI 中自动评估准确率、引用、泄露、延迟和成本。
- 将服务容器化部署到本地 K8s，配置探针、资源限制和故障恢复。

### 不要写

- 精通大模型、算法、Kubernetes 或 SRE。
- 主导生产级 AI 平台。
- 使用“提升效率 X%”，除非有一致口径的前后对照数据。
- 把阅读笔记数量当作项目成果。

## 十、执行优先级：只做能改变求职结果的事

### 立刻停止

- 继续新增长篇 AI 概念文档。
- 为补 Day 50-75 而抄写计划。
- 同时学习 LangChain、LlamaIndex、AutoGen、多个向量库和多个模型平台。
- 在 ACK 云资源尚未稳定前追求完整云上架构。

### 只保留一个主线

> CI 失败分析 Agent，从确定性解析开始，逐步接模型、RAG、工具、评测和部署。

### 每周必须产出的四类证据

1. 一个可运行命令。
2. 一组通过或被明确解释的测试。
3. 一个真实失败与修复记录。
4. 一个能用于面试讲述的指标或权衡。

## 十一、最终判断

当前仓库已经证明你有持续学习、文档整理和基础 CI/CD 能力，也说明 DevOps 到 Agent 的方向选择是对的。但它还没有证明你能独立交付 AI 应用。

最现实的上岸路径不是转算法，而是：

> 用现有 DevOps 场景做差异化 Agent 作品，先进入 AI 应用、AIOps 或 Agent 平台相邻岗位，再用真实业务和生产经验向更高层级的平台工程与 Agent 工程发展。

如果只完成 8 周计划中的一半，至少应保住 W2、W3、W6 和 W7：确定性分析器、可替换模型层、自动评测、可部署服务。这四项最能把你从“学过 AI”变成“能做 AI 应用”。
